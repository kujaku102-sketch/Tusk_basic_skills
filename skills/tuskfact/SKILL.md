# `/tuskfact` — Tusk製品アーキテクチャ適合監査スキル

対象製品・Extensionの設計と実装が、Tuskアーキテクチャの**3大構造原則**に適合しているかを**「Stage 1: Skim（流し見）」→「Stage 2: 本レビュー」の二段階**で監査し、レポートおよび改善箇所リストを作成する。

> [!IMPORTANT]
> 本スキルは**読み取り専用（`read_only` / `review_only`）**で実行する。監査中に製品コードを直接書き換えてはならない。

---

## 監査の3大チェック軸

### 軸1: エラーコード規則の適合性 (`Error Code Compliance`)
- **基準**: `Tusk_core/ERROR_POLICY.md` および `Tusk_core/ERROR_CODES.md`
- **検査ポイント**:
  1. 構造化ログ出力が `[TUSK_FORCE_STOP]` / `[TUSK_MINOR_ISSUE]` / `[TUSK_PROGRESS]` の文法に従っているか（旧 `IDTASK_*` や文字列レガシーコード `STALL_30M` 等が残っていないか）。
  2. エラーコードが `[F|M][1-9][0-9]{2}` 形式（旧 `0XX` 番台の廃止）になっているか。
  3. **`1XX`〜`5XX`（Core指定領域）**の意味（`1XX`: Core、`2XX`: 作業/セッション、`3XX`: データ、`4XX`: 通信、`5XX`: プロセス/外部連携）を勝手に別用途へ流用していないか。
  4. 製品固有のエラーが **`6XX`〜`9XX`（製品自由領域）**に正しく割り当てられ、製品側のSpecまたは一覧表に明記されているか。

### 軸2: マイクロカーネル思想 (`Microkernel Architecture`)
- **基準**: 極小ランタイム（ディスパッチャ・状態管理・I/O境界のみ）＋ 疎結合モジュール呼び出し型
- **検査ポイント**:
  1. エントリポイントやコアランタイムが肥大化（God Object / 1ファイル数千行のモノリス化）していないか。
  2. ドメイン処理・アルゴリズム・外部変換器が独立したモジュール／プラグインとして切り出され、明確なインターフェース（関数契約・構造体・CLI引数）経由で呼び出されているか。
  3. モジュール間の循環依存や、下位モジュールから上位ランタイムへの逆参照がないか。

### 軸3: CUIベース＋GUIラッパーの完全分離駆動 (`CUI-First / Thin GUI Wrapper`)
- **基準**: コア機能はすべてCUI（CLI / Headless Engine）単体で完結・自動テスト可能であり、GUIはCUI/Engineを呼び出す薄い表示・入力ラッパーに徹していること
- **検査ポイント**:
  1. GUI層（Tauriフロントエンド、Win32/WPF/Qt画面、イベントハンドラ等）の中に、ビジネスロジック・ファイル解析・計算処理が直接書かれていないか。
  2. GUIを起動しなくても、CUIコマンドまたはヘッドレスAPIだけで全主要機能の実行・検証・バッチ処理が完結するか。
  3. GUIとCUI/Engine間の通信が、コマンドライン実行・IPC・構造化JSON等の明確な境界で分離されているか。

## 二段階実行フロー（Skim → 本レビュー）

自分の実行環境のプロファイル（`GEMINI_PROFILE.md` / `CLAUDE_PROFILE.md` / `CODEX_PROFILE.md`）に従い、必ず以下の2ステップを分けて実行する。

### Stage 1: 流し見スクリーニング (`role: skim` / 低推論・高速スキャン)
1. **静的スキャンスクリプトの実行**:
   まず付属の自動検査スクリプトを実行し、ディレクトリ構造・ファイル行数・エラーコード正規表現・GUI/CUI結合度の一次シグナルを収集する。
   ```powershell
   python extensions/Tusk_Basic_skills/skills/tuskfact/scripts/tuskfact_scan.py --target <対象ディレクトリパス> --json
   ```
2. **Skim判定（怪しい箇所の絞り込み）**:
   - 全ファイルを精読せず、スキャン結果とエントリポイント／ディレクトリ構成から**「問題なし（Pass）」「要精査（Suspect）」**を仕分ける。
   - **本レビュー担当へ渡す引き継ぎメモ（Suspectファイルと行番号リスト）**を作成する。

### Stage 2: 本レビュー深掘り検証 (`role: review` / 中〜高推論)
1. Stage 1 で抽出された **Suspect（要精査）ファイルだけ**をピンポイントで読み込む（Passした無関係なファイルは読まない）。
2. コードの実態を確認し、見せかけの分離（例：CUIコマンドはあるが実際はGUI側の関数にしか最新ロジックがない等）やエラーコードの誤用を確定させる。
3. 下記のフォーマットで **「Tuskfact 監査レポート＋改善箇所リスト」** を出力する。

## 出力レポート形式

```markdown
# Tuskfact アーキテクチャ適合監査レポート

- **監査対象**: `<target_path>`
- **総合判定**: `[PASS / NEEDS_REFACTOR / FAIL]`

## 1. サマリー判定（3大チェック軸）
| チェック軸 | Skim一次判定 | 本レビュー最終判定 | 要約 |
|---|---|---|---|
| 1. エラーコード規則 (`1XX-5XX` / `6XX-9XX`) | Pass / Suspect | **PASS / NG** | ... |
| 2. マイクロカーネル思想 (極小ランタイム＋モジュール分離) | Pass / Suspect | **PASS / NG** | ... |
| 3. CUIベース＋GUIラッパー完全分離駆動 | Pass / Suspect | **PASS / NG** | ... |

## 2. 改善箇所リスト (Actionable Refactor List)
| 優先度 | 分類 | 対象ファイル・箇所 | 現状の問題点 | 具体的な改善アクション | 推奨Intensity |
|---|---|---|---|---|---|
| High / Mid / Low | ErrorCode / Microkernel / CUI-GUI | `[file.py](file:///...)` | ... | ... | `LOW` / `MID` / `HIGH` |
```
